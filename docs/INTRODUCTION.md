# LLM-APM：LLM Agent 应用性能监控系统

> 设计理念、系统架构与应用场景

---

## 背景：为什么需要 LLM-APM

### LLM Agent 的复杂性

现代 LLM Agent（如 Claude Code、Codex、Copilot CLI）正在改变软件开发方式。一个典型任务可能涉及：

```
用户输入 → LLM 规划 → 工具调用链 → Subagent 嵌套 → 最终输出
```

这个过程中隐藏着大量复杂性：

| 问题 | 表象 | 难点 |
|------|------|------|
| 工具失败 | 任务未完成 | 不知道哪个工具失败、为什么失败 |
| 执行超时 | 等待过长 | 不知道哪个步骤耗时最长 |
| 成本过高 | 账单超标 | 不知道 Token 消耗在哪里 |
| 缓存低效 | 重复计算 | 不知道为什么缓存命中率低 |
| Subagent 深度过深 | 逻辑混乱 | 不知道调用链有多复杂 |

### 传统调试手段的局限

| 手段 | 局限 |
|------|------|
| 日志文件 | 文本分散，难以关联时间线 |
| 命令行输出 | 信息碎片化，无法回溯 |
| Transcript 文件 | JSONL 格式，人眼难以阅读 |
| LLM 自我分析 | 无法跳出自身视角 |

LLM-APM 的设计目标：**让 Agent 的执行过程可视化、可分析、可回溯**。

## 设计理念

### 从 APM 借鉴

LLM-APM 借鉴传统 APM（如 New Relic、Datadog）的核心思想：

| 传统 APM | LLM-APM |
|----------|---------|
| Request → Response trace | Prompt → Output trace |
| API call timing | Tool execution timing |
| Error rate monitoring | Tool failure detection |
| Resource consumption | Token/Cost tracking |
| Service dependency | Subagent nesting |

### 差异化定位

与传统 APM 不同，LLM-APM 针对 Agent 特性设计：

| 特性 | 说明 |
|------|------|
| **Turn 组织** | 按"用户输入 → Agent 响应"轮次组织，而非按 API 调用 |
| **工具语义** | 理解工具类型（Read、Write、Bash），而非视为黑盒 |
| **Subagent 深度** | 追踪嵌套调用链，而非扁平化展示 |
| **智能根因推断** | 自动推断异常原因，而非仅展示错误 |

## 系统架构

### 数据采集层

```
┌─────────────────────────────────────────────────────────────┐
│                      CLI Agents                              │
│   Claude Code | Codex | Copilot CLI                          │
└─────────────────────────────────────────────────────────────┘
         │                │                │
         │ Hooks (HTTP)   │ JSONL files    │ JSONL files
         │                │                │
         ▼                ▼                ▼
```

**双通道采集设计**：

| 通道 | 数据源 | 时机 | 内容 |
|------|--------|------|------|
| **Hooks** | HTTP POST | 实时 | 工具调用、错误、用户输入 |
| **JSONL Watcher** | 文件监控 | 近实时 | 对话内容、Token 统计、模型信息 |

为什么需要双通道？

- Hooks 提供精确的时间戳和错误标记
- JSONL 提供完整的对话内容和 Token 统计
- 两者互补，构建完整执行画像

### 分析引擎层

```
┌─────────────────────────────────────────────────────────────┐
│                   llm-apm-server                             │
│                                                              │
│  ┌────────────┐ ┌────────────┐ ┌────────────────────────┐  │
│  │   Handler  │ │  Watcher   │ │   Analysis Engine      │  │
│  │            │ │            │ │                        │  │
│  │ Hook接收   │ │ JSONL监控  │ │ 9种异常检测规则        │  │
│  │ 解析存储   │ │ 实时解析   │ │ 根因推断引擎           │  │
│  │ SSE广播    │ │ 去重处理   │ │ 关键事件筛选           │  │
│  └────────────┘ └────────────┘ └────────────────────────┘  │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐  │
│  │              SSE Broadcaster                          │  │
│  │  实时推送：错误、异常、慢工具                         │  │
│  └──────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**异常检测规则体系**：

| 规则类型 | 触发条件 | 严重级别 | 设计意图 |
|----------|----------|----------|----------|
| slow_tool | > 30s | medium | 定位性能瓶颈 |
| slow_tool_critical | > 60s | high | 识别严重阻塞 |
| tool_failure | 返回错误 | high | 立即感知失败 |
| error_spike | 5min > 3次 | medium | 检测连锁失败 |
| high_cost | > $1 | medium | 成本预警 |
| cache_miss_spike | < 50% | low | 优化提示 |
| subagent_depth | > 3层 | medium | 复杂度预警 |
| turn_loop | > 20轮 | low | 循环检测 |
| timeout | 超时 | high | 资源问题 |

**根因推断逻辑**：

```
异常事件 → 提取上下文 → 关联分析 → 匹配模板 → 推断原因 → 生成建议
```

例如：检测到 `tool_failure` + `error_spike`，推断为"连续工具失败，可能存在环境配置问题"。

### 数据存储层

```
┌─────────────────────────────────────────────────────────────┐
│                     GreptimeDB                               │
│                                                              │
│  数据表：                                                    │
│  • apm_hook_events   - Hook 事件记录                        │
│  • apm_messages      - 对话消息记录                         │
│  • apm_anomalies     - 异常检测结果                         │
│  • apm_turns         - Turn 边界记录                        │
└─────────────────────────────────────────────────────────────┘
```

**为什么选择 GreptimeDB**：

| 特性 | 优势 |
|------|------|
| 时序数据库原生 | 高效存储时间戳索引数据 |
| SQL 接口 | 熟悉的查询语法，无学习成本 |
| 嵌入式模式 | 本地部署零配置，生产可远程 |
| 自动 TTL | 数据过期自动清理 |

### 展示层

```
┌─────────────────────────────────────────────────────────────┐
│                      Dashboard                               │
│                                                              │
│  ┌────────────┐ ┌────────────┐ ┌────────────────────────┐  │
│  │  Sessions  │ │  Problems  │ │      Analysis          │  │
│  │            │ │            │ │                        │  │
│  │ Session列表│ │ 异常列表   │ │ Token/成本统计         │  │
│  │ 执行时间线 │ │ 根因推断   │ │ 延迟分布分析           │  │
│  │ Turn组织   │ │ 一键定位   │ │ 工具调用热力图         │  │
│  └────────────┘ └────────────┘ └────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**三视图设计意图**：

| 视图 | 目的 | 核心交互 |
|------|------|----------|
| **Sessions** | 执行回放 | 点击 Session → 展开时间线 → 查看工具详情 |
| **Problems** | 问题定位 | 点击异常 → 查看根因推断 → 一键跳转时间线 |
| **Analysis** | 全局洞察 | 统计卡片 → 模型分布 → 成本排名 → 工具热力图 |

**一键跳转机制**：从 Problems View 点击异常，自动跳转到 Sessions View 并高亮异常段，实现"问题定位 → 上下文查看"闭环。

## 数据流

### Hook 事件流

```
1. Agent 触发 Hook（如 PreToolUse）
   │
   ▼
2. HTTP POST /api/hooks
   │
   ▼
3. Server 解析 payload，提取字段
   │
   ▼
4. 写入 GreptimeDB apm_hook_events 表
   │
   ▼
5. Analysis Engine 实时检测异常
   │
   ▼
6. 如检测到异常，写入 apm_anomalies 表
   │
   ▼
7. SSE 推送关键事件到前端
```

### JSONL 监控流

```
1. 监听 ~/.claude/projects/*.jsonl 文件变化
   │
   ▼
2. 解析新增 JSONL 行
   │
   ▼
3. 提取 message 内容、Token 统计、模型信息
   │
   ▼
4. 写入 GreptimeDB apm_messages 表
   │
   ▼
5. 去重处理（避免 Hook 和 JSONL 重复写入）
```

### Turn 边界划分

```
UserPromptSubmit ──→ Turn 开始
   │
   ▼
[工具调用链]
   │
   ▼
AssistantResponse ──→ Turn 结束
```

Turn 边界用于：
- 统计每轮 Token 消耗
- 计算每轮成本
- 检测 Turn 循环异常

## 应用场景

### 场景一：调试工具失败

**问题**：Agent 执行任务时失败，不知道哪个工具出错。

**LLM-APM 方案**：
1. Problems View 显示 `tool_failure` 异常
2. 点击查看根因推断："Read 工具失败，文件不存在"
3. 一键跳转到 Sessions View，查看完整上下文
4. 发现 Agent 尝试读取的文件路径错误

### 场景二：优化执行时间

**问题**：Agent 执行某些任务很慢，想找到瓶颈。

**LLM-APM 方案**：
1. Analysis View → TTFT 分布图
2. 发现 Bash 工具平均执行时间 15s
3. Sessions View 查看具体 Bash 调用
4. 发现命令包含不必要的 `sleep`
5. 优化命令，执行时间降至 2s

### 场景三：控制成本

**问题**：LLM 成本过高，想知道 Token 消耗在哪。

**LLM-APM 方案**：
1. Analysis View → 成本排名 Top 10
2. 发现 Session A 消耗最多
3. 展开 Sessions View 查看 Session A 时间线
4. 发现 Subagent 嵌套过深，导致重复调用
5. 优化提示词，减少 Subagent 使用

### 场景四：分析缓存效率

**问题**：提示词缓存命中率低，不知道为什么。

**LLM-APM 方案**：
1. Analysis View → 缓存效率分析
2. 发现命中率仅 30%
3. 查看模型分布，发现使用多个不同模型
4. 不同模型导致缓存失效
5. 统一使用同一模型，命中率提升至 70%

### 场景五：研究 Agent 行为

**问题**：想研究 Agent 在特定任务上的行为模式。

**LLM-APM 方案**：
1. Analysis View → 工具调用热力图
2. 发现 Agent 偏好使用 Edit 而非 Write
3. Sessions View 查看具体 Edit 调用
4. 发现 Edit 更精确，但多次调用合并可优化
5. 总结 Agent 在代码修改任务的行为模式

## 技术特点

### 轻量化设计

| 方面 | 设计 |
|------|------|
| 部署 | 单二进制 + 嵌入式数据库 |
| 依赖 | Go 标准库为主，无重型框架 |
| 前端 | 原生 JS，无构建步骤 |
| 存储 | GreptimeDB 自动管理 TTL |

### 实时性保障

| 机制 | 说明 |
|------|------|
| HTTP Hook | Agent 同步触发，无延迟 |
| SSE 推送 | 关键事件实时到达前端 |
| JSONL Watcher | 文件变化毫秒级感知 |

### 可扩展预留

| 扩展点 | 预留设计 |
|--------|----------|
| 多租户 | 表预留 `tenant_id` 字段 |
| 多 Agent | 支持 Codex、Copilot CLI 数据格式 |
| 自定义规则 | Analysis Engine 可插拔规则 |
| 远程部署 | 支持远程 GreptimeDB 连接 |

## 与其他工具对比

| 工具 | 定位 | 与 LLM-APM 关系 |
|------|------|-----------------|
| **Claude Code Transcript** | 完整对话记录 | LLM-APM 的数据源之一 |
| **LLM API Dashboard** | API 调用监控 | 互补：API 层 vs Agent 层 |
| **LangSmith** | LangChain 追踪 | 互补：框架层 vs 工具层 |
| **传统 APM** | 服务监控 | 互补：后端服务 vs Agent |
| **LLM Observatory** | 模型评估 | 互补：模型质量 vs 执行过程 |

LLM-APM 定位：**专注 Agent 执行层，填补 Transcript 和 API 监控之间的空白**。
